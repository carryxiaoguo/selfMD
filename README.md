# selfMD

一个所见即所得的实时预览 Markdown 编辑器。个人自用，从零实现。

## 它是什么

**纯文本是唯一数据源。** 所有渲染——标题、代码块、表格、图片、公式、图表——
都只是叠加在 Markdown 文本之上的视图层。保存到磁盘的永远是用户敲下的原始字节，
一个字符都没被改写。这带来三个直接后果：

- 任何编辑器都能打开这些文件，任何版本控制都能正常 diff
- 渲染出问题不会损坏文档，最坏情况是"看起来像纯文本"
- 换掉这个编辑器，文件原样可用

**技术栈**：Electron 33 + TypeScript + CodeMirror 6。
编辑器内核用 CodeMirror 而不是自研——它的状态模型（不可变状态 + 事务）
天然适合"渲染层只读文档、绝不改文档"这套架构。

**功能范围**参考了主流 Markdown 编辑器的通行做法，完整规格见
[`功能清单.md`](./功能清单.md)。本项目是**独立实现**。

### 打包

```bash
pnpm build           # 先构建到 out/
npx electron-builder # 按 package.json 的 build 段打包到 release/
```

**测试文件不会被装进安装包。** `build.files` 是**白名单**，只收两样：

```json
"files": ["out/**/*", "package.json"]
```

`fixtures/`、`scripts/`、`src/`、`resources/` 都不在里面——白名单比黑名单可靠：
新增目录时默认**不进包**，而不是默认进包、等着谁记得去排除。
后面那几行 `!` 是**双保险**，万一将来有人把白名单放宽，测试文件也不会顺带溜进去。

> **一个容易忽略的坑：运行时依赖会整包塞进安装包。**
>
> electron-builder 会把 `dependencies` 里的包原样复制进 asar，而
> `devDependencies` 不复制。但渲染层的依赖已经被 Vite 打包进 `out/` 了——
> 所以 `katex`、`mermaid` 挂在 `dependencies` 里等于**装两份**，
> 其中 `mermaid` 一个就是 116.7 MB。
>
> 判断规则很简单：**被 Vite 打进 `out/` 的放 `devDependencies`，
> 只有主进程用 `require` 在运行时加载的才放 `dependencies`**。
> 本项目主进程不依赖任何第三方包，所以 `dependencies` 是空的。

### 为什么计数要分两套

**解析树计数覆盖整篇文档，DOM 计数只覆盖视口**——CodeMirror 会虚拟化长文档，
视口外的行根本没有 DOM。两个数放在一起，才能区分"装饰没生效"和
"内容在屏幕外"。

冒烟测试还会把窗口调到 1600px 高，让紧凑样本整篇落在一屏内，
从而让两组数字可以直接逐项对账。样本文件必须保留 Markdown 所需的空行，
**不能为了压缩行数而删空行**——删掉之后块级结构会互相吞并
（实测：表格末行加紧随的 `---` 会被解析成 Setext 标题，整个表格从语法树里消失）。

### 取样时机：偶发失败最消耗信任

计数必须在装饰**落到 DOM 之后**取。一开始用的是固定 400ms 延时，
结果每隔几次就会冒出"某类装饰缺失"的假失败：

```
· 渲染 列表圆点：期望 3，实际 缺失
· 渲染 表格竖线：期望 6，实际 缺失
```

功能是好的——只是**取样太早**。这类偶发失败比稳定的失败更糟：
它让人开始怀疑整套测试，最后连真的回归也被当成"又抽风了"。

改成**轮询到计数稳定**：连续三次取到同一个值才继续。
装饰是分批落下去的，两次相同还可能是碰巧。

`dump-locale.mjs` 从任意外部语言包读取键值对照，
输出逐条对照。**本项目全部界面译法都以此为准**，理由见下节。

`dump-tree.mjs` 把 Lezer 的解析树按缩进打印出来，并汇总所有节点名。

**为什么需要它**：装饰层是按节点名分派的，节点名写错会**静默失效**——不报错、
不生效，是最难排查的一类问题。实现块级装饰之前，先用它确认了真实节点名，
也因此提前发现了两个反直觉的事实：

- **YAML 前置元数据在语法树里根本不存在。** 首尾的 `---` 被解析成
  `HorizontalRule`，元数据正文被解析成普通 `Paragraph`，`键: 值` 那两行则被拼成 `SetextHeading2`（Setext 二级标题）。
- **`$$` 数学块同样不存在**，被当作普通段落。

所以这两类块只能按行手工扫描，代码在 `live-preview/block.ts`。

> **关于启动脚本。** `pnpm dev` 与 `pnpm smoke` 都经由 `scripts/dev.mjs` /
> `scripts/smoke.mjs` 启动，而不是直接调用 `electron-vite`。原因是：只要环境里
> 存在 `ELECTRON_RUN_AS_NODE=1`（任何会派生子进程的 Electron 宿主应用都会设置它），
> Electron 可执行文件就会退化成纯 Node.js，应用会崩在
> `Cannot read properties of undefined (reading 'app')`。启动脚本会删掉这个变量，
> 让命令在任何终端和 CI 里行为一致。

### 唯一重要的架构决策

**Markdown 文本是唯一真实数据源，渲染只是叠加在它之上的装饰。**

这解释了一个现象：`内部渲染层` 的模块 `20` 是 CodeMirror 5，
`contenteditable` 出现 141 次，`ProseMirror` 出现 **0** 次，另有一层自研的
"brush" 层把装饰 DOM 画在纯文本缓冲之上。这套架构让编辑器能在源码与预览之间
无损切换、文件能逐字节往返的原因。

对本实现的约束：

- 没有富文本文档模型。ProseMirror / Tiptap 那类设计会让 Markdown 往返有损，
  并把"源码模式"变成一次转换而不是一个视图。
- 装饰**永远不允许**改写文档。
- 光标所在块的语法标记保持可见，其余位置折叠为零宽。这**按行**判定而不是按节点判定——正因如此，光标永远不会落进一个被折叠掉的标记里。

见 `src/renderer/src/editor/live-preview/index.ts`。

### 装饰层内部：三个必须知道的陷阱这三条都是实现过程中被验证机制抓出来的真实缺陷，不是理论担忧。

**① 语法高亮与装饰层必须用不同的 class 前缀。**
语法高亮用 `cm-tok-*`，装饰层用 `cm-md-*` / `cm-lp-*`。早先两者共用类名，
导致同一段文字被标记两层——解析树里 `StrongEmphasis=1`，DOM 里
`.cm-md-strong` 却有 4 个。分开之后既能统计对账，主题作者也能区分
"我要改源码里的标记颜色"和"我要改渲染后的加粗"。

**② 不能用 `RangeSetBuilder` 构建装饰。**
它只接受**互不重叠**的区间，遇到嵌套直接抛
`Ranges must be added sorted by 'from' position and 'startSide'`。
而嵌套是常态：`**加粗里的 *斜体***` 就是 StrongEmphasis 套着 Emphasis。
必须用 `RangeSet.of(区间, true)`。
早先为规避该异常而加的"重叠即跳过"过滤，又把内层强调整条丢掉了——
解析树数得到 2 个 `Emphasis`，屏幕上只有 1 个斜体。

**③ 隐藏标记必须按行判定。**
`**加粗**` 的两个 `**` 折叠为零宽后，光标若落进去就会"消失"。
按"光标所在行不隐藏"判定，这个问题在结构上就不存在。

### 从 继承的其他设计决策

| 决策 | 依据 |
|---|---|
| 用户数据放在 `<userData>/{conf,themes,backups,drafts,images}` | 沿用通用的目录布局，文档与肌肉记忆都能迁移 |
| `conf.user.json` 支持 JSONC 并保留未知键 | 这类配置文件普遍带 `//` 注释，手工编辑必须能往返 |
| 主题是 `.css` 文件，且只覆盖 token | 让第三方主题保持小巧、向前兼容；对应通用的 `themes/` 目录 |
| 当前主题经自定义协议加载 | 主题里的相对 `url(...)` 必须相对主题目录解析，否则背景图失效——这正是 `应用私有协议 ` 承担的职责 |
| 剪切/复制/粘贴用 Electron **role** 而非 IPC | role 直接作用于聚焦的 `webContents`，保住原生剪贴板、输入法与选区行为 |
| 未移植的菜单项**渲染为禁用** | 菜单因此成为实时进度图，而不是静默无操作的陷阱 |
| 文档与配置写入用"临时文件 + 改名" | 写入中途崩溃不得截断用户文件 |
| 删除走系统回收站 | 误操作可恢复 |
| 编辑命令一律走"切换语义" | 对已加粗的选区再点一次加粗应当是取消；菜单无需维护勾选状态 |

### P3 写作手感：三个值得记录的取舍

**① 智能标点必须看语法树，不能只看字符**

`--` 转成 `–` 在正文里是排版改进，在代码块里则是**改坏代码**。所以转换前先用
`syntaxTree().resolveInner()` 判断光标是否落在代码围栏、行内代码、URL 或注释里，
是则一律不转换。同一段逻辑还要处理另一种冲突：**行首的 `---` 是水平分割线，
也是 YAML 前置元数据的围栏**，换成破折号会直接毁掉文档结构。

判断方法是"连字符之前还有没有正文"，而不是"整行是不是只有连字符"——后者要预知
用户接下来敲什么，做不到。代价是行首永远得不到连接号，这是刻意取舍：**结构正确
优先于标点美观**。

**② 格式命令要在撤销栈里独占一步**

没有处理时，紧接着打字之后的 Ctrl+B 会与前面的输入合并成同一组，于是 Ctrl+Z
一次把加粗和刚才敲的半句话一起撤销——用户想要的是"撤掉加粗"，不是"撤掉一段"。
修法是给每个格式命令加 `annotations: isolateHistory.of('full')`。

注意它**不是** `TransactionSpec` 的字段（写成 `isolateHistory: 'full'` 会编译失败），
而是 `@codemirror/commands` 导出的 `AnnotationType`，必须走 `annotations`。

**③ 自动配对刻意不配对星号**

配对的字符集只收括号与引号，不含 `*` `_` `~`。这三者在 Markdown 里首先是块级
语法的开头：敲 `*` 想开无序列表、敲 `~` 想开代码围栏时被自动补成一对，反而要先
删掉多余的半个。星号成对是"加粗"命令该干的事，不该由配对器抢着做。

另外 `closeBrackets()` **不接受参数**——配对字符是通过语言数据配置的，
写成 `closeBrackets({ brackets })` 会直接编译失败。

### P4 图片管线：端到端测试抓出的两个真实缺陷决策逻辑（图片该放哪、要不要搬运）全部做成了**纯函数**并逐条断言，
这类 bug 靠手点几乎不可能穷举。但纯函数正确**不等于**链路正确——
下面两个缺陷都是靠"让应用真的插一张图、再把文档内容打印出来"才暴露的：

**① 图片引用被写到了 YAML 前置元数据之前**

打开文档后光标默认停在文首，直接插入会得到：

```
![样本](图/样本.png)---⏎image-folder: 图⏎---⏎…
```

前置元数据不再是文档开头，整块 YAML 立刻失效——文档级图片目录、根路径
这些设置全丢。修法是插入前把插入点推到元数据块之后。

**② 中文路径被整段百分号编码**

第一版用 `encodeURI`（这是最直觉的做法），于是
`图/样本.png` 写成 `%E5%9B%BE/%E6%A0%B7%E6%9C%AC.png`——能加载，
但完全读不出来，也没法手改。

现在只转义**真正会破坏解析**的字符（空白、`#`、`?`、`%`、尖括号等），
非 ASCII 原样保留。这是**有意偏离 ** 的一处：现代 Markdown 渲染器
与浏览器都能正确处理 UTF-8 路径，可读性更重要。

### P4 里几处刻意的判断

| 决定 | 理由 |
|---|---|
| 剪贴板**优先按文件**读取 | Windows 上从资源管理器复制图片时，剪贴板同时提供原图路径与一张可能是压缩预览的位图；先取位图会让用户粘进来一张糊图 |
| 剪贴板位图在"不做特殊处理"策略下落到 `<userData>/images/` | 位图没有磁盘来源，而"保持原路径"对一个只在内存里的对象无从谈起。主流编辑器普遍这么做（用户数据目录下确实存在一批这类文件） |
| 复制进目标目录做成**单个原子 IPC**，而不是"先查存在再复制" | 后者在并发插入时会两边都判定"不存在"，后写的覆盖先写的 |
| 重名一律追加 `-1`、`-2`，绝不覆盖 | 图片被静默覆盖，用户往往几周后才发现某张图变成了另一张 |
| 设置图片文件夹写**相对路径** | 文档连同图片一起搬家时引用才不会断 |
| 粘贴处理器只在**有把握**时接管 | 判错会导致普通文字粘贴被吞掉——用户会以为编辑器坏了。所以只要有非空文本就放行给默认行为 |

## 偏好设置

`Ctrl+,` 打开。37 项设置、5 个分区，带跨分区搜索。

### 声明式设置表界面**不硬编码任何一项**，完全照着
[`src/shared/settings-schema.ts`](./src/shared/settings-schema.ts) 渲染：

```ts
{ 键: 'livePreview', 类型: '开关', 标签: '即时渲染', 说明: '…' }
```

加一项设置只动这张表，不必同时改界面、类型与应用逻辑三处。

这样做还有个更实在的好处：**"表里的键是不是真的存在"可以被断言**。
写成 `livePreveiw` 这种笔误时，界面照样画得出来、点下去毫无反应，
靠肉眼几乎发现不了。验证里有 6 条断言盯着这张表：

```
偏好设置·键名全部有效     =>  有效       ← 抓笔误
偏好设置·无重复项        =>  无重复     ← 重复键会让两项互相覆盖
偏好设置·下拉均有选项     =>  均有       ← 否则渲染出空下拉框
偏好设置·数值区间自洽     =>  自洽       ← 否则值被夹在边界上出不来
偏好设置·标签均含中文     =>  均含
偏好设置·默认值在选项内   =>  在选项内   ← 否则打开面板就是"选了个不存在的项"
```

### 界面细节

- **搜索跨分区平铺**，每行带一个分区名角标——否则用户不知道这一项属于哪里
- **数字框用 `change` 而不是 `input`**：用 `input` 时拖箭头或长按删除键会在每一个中间值上写一次设置，产生一串无意义的历史
- **只读项视觉上要能看出改不了**（例如「当前主题」由「视图 → 主题」决定），
  否则用户会一直点它
- 改设置一律走 `settings.patch` 并 await——渲染层的 `settings` 只是主进程状态的缓存，直接改本地对象会被下一次广播冲掉（这个坑在编辑模式那轮踩过）

### 智能标点：两种转换时机

"何时转换"是**三选一**：输入时 / 渲染时 / 关闭。三者互斥，所以菜单里用 radio
而不是 checkbox——用 checkbox 会让人以为可以同时开两个，而实际只有后设的那个生效。

| 模式 | 文档里存的 | 屏幕上看到的 |
|---|---|---|
| 输入时转换 | `“` `—` `…` | 同左 |
| **渲染时转换** | **`"` `---` `...`** | `“` `—` `…` |

渲染时转换适合"文件要保持纯 ASCII、但看着要舒服"的场合。

**两套规则必须一致**，所以引号判断复用同一个函数——各写一份的话，
同一段文字在两种模式下会得到**不同方向**的引号，而且极难发现。

扫描是**逐字符推进**而不是逐个正则匹配：`---` 必须优先于 `--`，
用正则轮流试会先命中 `--`，把破折号拆成"连接号 + 连字符"——
而拆出来的结果看起来还挺像回事，不会有人怀疑。

```
标点·三连是破折号            =>  ---→—
标点·两连是连接号            =>  --→–
标点·四连拆成破折号加连字符   =>  ---→—      ← 只产生一段替换
标点·段首是左引号            =>  "→“ "→”
标点·撇号                   =>  '→’         ← don't 里的不是引号
标点·已是弯引号则不动         =>  （无）
```

**只在非活动行生效**：正在编辑的那一行必须显示真正的字符，否则用户敲下 `"`
却看到 `“`，会以为文档里存的就是弯引号。这与行内标记"活动行露出源码"是同一条规则。
行内代码里的引号与连字符也跳过——那是内容本身。

样式上**盖一层，而不是改宽度**：原字符留在原地并保持自己的宽度
（`color: transparent` 只藏颜色，不藏占位），排版字符用绝对定位的 `::after`
叠在上面。这样 CodeMirror 量到的仍是原字符的宽度，光标位置不受影响；
若改用 `font-size: 0` 让 `::after` 撑开宽度，虽然显示更"准"，
却会让测量结果随字形变化，打字时光标会轻微跳动。

## 拼写检查

由 **Chromium 自带的拼写检查器**完成——它提供红波浪线与右键"建议替换"，
不必自己实现词典与算法。**默认关闭**：中文没有可用的拼写词典，
中文用户开着它只会看到满屏红波浪线。

设置项里可以配词典语言（`en-US, en-GB` 这样逗号分隔）。

> **两个容易踩的点。**
>
> ① **词典语言必须在窗口加载内容之前设置。** 之后再改，已经渲染的文本
> 不会重新检查——用户会以为"改了没生效"。所以设置在变更时应用，
> 而设置项的说明里写明了"改完需要重新打开文档"。
>
> ② **不可用的语言要过滤掉。** Chromium 只带一部分词典，传一个它不认识的
> 值会让整个调用失败，连原本能用的语言也一起丢掉。所以先与
> `availableSpellCheckerLanguages` 取交集；一个都不匹配时回退到英语——
> 有检查总比静默失效好。

编辑器侧还**显式声明**了 `spellcheck` 属性：Chromium 对可编辑区域默认开启，
而 CodeMirror 既不设置也不清除它，于是"主进程开了、这里没开"时行为取决于
浏览器默认值，不受我们控制。显式写出来，开关才只由设置决定。

断言落在"设置 → DOM 属性"这条链路上：

```
编辑模式   专注行=3 专注类=true … 拼写开启=true 拼写关闭=false
```

断链不会报错，只是红波浪线不出现——而用户多半会以为"这个词本来就拼对了"。

## 写作模式与自动保存

### 专注模式

只让光标所在的那一块保持清晰，其余淡化到 28%。类名沿用通用命名：
`body.on-focus-mode` + 当前块上的 `.md-focus`（内置主题里出现 37 次，
是除 `#write` 之外最常被主题挂钩的选择器）。

**一种常见实现是 100ms 轮询**：

```js
exitFocusModeTimer = setTimeout(enterFocusMode, 100)
```

进入专注模式后每 100 毫秒把自己重新跑一遍，靠反复重刷跟上光标移动。
这里不需要——CodeMirror 会把文档与选区的变化推给我们，直接在 `update` 里
重算即可。轮询既费电，又会在快速移动光标时慢半拍。

### 打字机模式让光标行始终停在视口垂直中央。

**另一种做法是动态注入内联样式**：算出 `(内容高度 - 单行高度) / 2`，
塞进一个 `<style id="write-style">` 的 `#write { padding-top: … }`，
靠加内边距把首行"顶"到中间。

这里直接用 `EditorView.scrollIntoView(pos, { y: 'center' })`——语义就是
"把这一行滚到垂直中央"，不必自己算高度，窗口尺寸变化时也不会失准。

只在**行号真的变了**时才滚：否则在一行内左右移动光标也会触发，
用户会看到画面无谓地跳动。

### 自动保存与崩溃恢复

草稿写在 `<userData>/drafts/`。每份草稿由**内容文件 + 元数据文件**一对组成：

> 分成两个文件而不是塞进一个 JSON：内容是纯文本，崩溃后用记事本就能直接
> 打开抢救；塞进 JSON 的话转义一坏就全丢了。

- **防抖 3 秒**——只在停下来之后写一次，连打期间不写盘
- **关窗前强制落一次**——即使用户选了"不保存"也落：关窗是最后的机会，
  写一份草稿的成本几乎为零，而它可能救回一整篇文章
- **保存成功后清掉草稿**，但**只在内容一致时清**
- 启动时列出可恢复的草稿，让用户选「恢复 / 稍后再说 / 丢弃」

> **一个真实的竞态。** 保存是异步的，期间用户可能又敲了几个字。
> 如果保存成功后无条件删草稿，那部分新内容就永远丢了。
> 所以比对的是"草稿内容 === 刚保存的内容"，不一致就保留。
> 这条守卫有专门的断言（`内容不一致时保留草稿`）。

> **另一个真实的竞态（在验证代码里）。** 编辑模式自测最初直接改渲染层的
> 本地 `settings` 对象，结果前一个自测触发的设置广播在半路落地，
> 把刚设上的 body 类冲掉了——症状是"装饰生效了但类没生效"。
> 渲染层的 `settings` 只是主进程状态的**缓存**，任何一次广播都会覆盖它；
> 改设置必须走 `settings.patch` 并 await。

## 导出



### 两条路

| 格式 | 实现方式 |
|---|---|
| **HTML** | **自己渲染**——遍历已有的 Lezer 语法树生成 HTML |
| **PDF** | 自己渲染 HTML，再交给 Chromium 打印（Electron `printToPDF`，无需外部程序） |
| Word / LaTeX / ePub / RTF / ODT | **委托 Pandoc**；检测不到就把菜单项置灰并说明原因 |

这个分工不是随意的：HTML 与 PDF 能自给自足（Electron 自带 Chromium 打印），
而其余格式交给 Pandoc——它已经把这些格式的转换做到了工业级，
自己实现既无必要也不现实。

**置灰而不是隐藏**：用户看不到 Word 会以为软件没这个功能；看到它灰着
并附一句「安装 Pandoc 后可用 Word 等格式」，才知道该怎么开启。

### 渲染器为什么自己写

`src/shared/markdown-html.ts` 遍历**编辑器已经在用的那棵语法树**，而不是另引
一个 Markdown 库。两个理由：

1. **与实时预览同源**——用两个不同的解析器，迟早会出现"屏幕上是一种、
   导出是另一种"的偏差，而且极难排查。
2. **是纯函数**——吃一段文本、吐一段 HTML，因此可以逐项断言输出，
   不必真的导出一次再肉眼比对。

> **打印解析树才发现的四个错误。** 最初凭印象写节点名，26 项断言里错了 4 项：
>
> | 症状 | 真实结构 | 错误假设 |
> |---|---|---|
> | 标题多了前导空格 | `HeaderMark` 只是 `#`，`0..5` = `# 标题一` | 以为标记含空格 |
> | 删除线残留 `~~` | 节点名是 **`StrikethroughMark`** | 写成了 `EmphasisMark` |
> | 链接多出地址与标题 | `URL`/`LinkTitle` 是 `Link` 的子节点 | 没排除，被当正文再输出一遍 |
> | 表格对齐丢失 | 分隔行是**单个**节点，内部无单元格 | 以为里面有 `TableCell` |
>
> 这类错误的共同点是**输出的 HTML 仍然"看起来对"**——多一个空格、
> 多一串地址，扫一眼很难发现。所以断言必须落在结构上，
> 而不是"导出的文件能打开就算成功"。

### 导出态的样式

照搬通用的导出态规则，逐条都有明确用途。
其中**只有一条绝对不能省**：

```css
.selfmd-export * { -webkit-print-color-adjust: exact; print-color-adjust: exact; }
```

没有它，Chromium 打印 PDF 时会**丢弃所有背景色与背景图**——代码块、引用块、
表格斑马纹全部变白底。导出的 PDF 与屏幕所见完全不同，而用户只会认为
"导出功能坏了"，很难联想到是打印色彩策略。验证里专门有一条盯它。

### `@include-when-export`

一条非标准指令，语法沿用通行写法：

```css
@include-when-export url(https://fonts.googleapis.com/css?family=Open+Sans:...);
```

**语义**：地址只在导出时内联，屏幕上编辑时不加载。内置主题用它引远程字体——
屏幕上不加载（离线可用、不卡首屏），导出时才带上，因为导出的文件要在
**别人的浏览器**里打开，那时未必有本地字体。

取不到资源时**整行删掉**而不是留着：这不是浏览器认识的规则，
留着只会变成一条无效样式，还容易让人以为它生效了。

### 自包含

- 本地图片默认**内嵌成 base64**，导出单个 HTML 文件即可分享。
  远程图片保持原样——用户放远程地址本来就不指望它离线可见。
- 样式把三层级联（主题 → `base.user.css` → `<主题>.user.css`）全部内联，
  且 `@import` 递归展开（带 8 层深度上限，防环路）。
- 附带侧边目录（`selfmd-export-sidebar`），长文档转成 HTML 后好导航；
  打印时自动隐藏。

## 图片管线

### 图片渲染：一个被纯函数断言完全盖住的缺口图片管线（存储策略、插入、引用生成）早就做完了，118 条纯函数断言全绿——
但**屏幕上从来就没出现过图片**，一直只显示 `![替代](地址)` 的源码。
渲染这一步整个缺失，而所有断言都覆盖不到它。

现在装饰层把 `![…](…)` 整段换成真实的 `<img>`，文档一个字符都没动。
光标**进入这段语法内部**时才露出源码——不像别的行内标记那样按"整行"判断：
图片通常独占一行，按行判断会让光标停在段落里任何位置都让图片变回源码，
等于图片一直在闪。

**地址解析**是这一步的关键，也是最容易出错的地方：文档里写的是相对路径
（`图/样本.png`），必须拼到文档所在目录上才找得到文件。

> `设置文档目录` 必须在 `setDocument` **之前**调用。文档内容一进编辑器就会构建
> 装饰，那时若基准目录还是上一篇文档的，图片会先渲染成"无法显示"，
> 要等重绘才恢复——表现为图片闪一下。

**失败要说明原因**，不能只留一个破图图标：破图会让人以为图片文件坏了，
而真实原因常常是"文档还没保存，相对路径没有基准目录"。所以占位文字写明
「无法显示图片」并把鼠标悬停提示写成下一步该做什么。

验证里把图片分三类统计，因为**"没渲染"与"渲染了但加载失败"的修复方向完全不同**：

```
图片渲染解析 4 个 · 成图 3 张 · 失败占位 1 个 · 独占行 3 行
```

素材里四种情况各一份：相对路径能加载的、指向不存在文件的、远程地址的、
以及夹在句子中间的。独占一行的会被居中成块，行内那张不带这个类。

### 图床上传

本编辑器不内置任何图床 SDK，唯一的 HTTP 端点是 PicGo/PicList 在本机
监听的 `http://127.0.0.1:36677/upload`，其余全部委托外部命令行程序。
本项目沿用同样的分工——图床协议五花八门，自己实现等于给每家写一个适配器。

| 上传器 | 方式 |
|---|---|
| PicGo / PicList（应用） | `POST http://127.0.0.1:36677/upload`，body `{list:[…]}` |
| 连不上时 | 用配置的路径启动应用，**等 5 秒后重试一次**（应用启动需要时间，立刻重试必然失败） |
| PicGo（命令行） | `chcp 65001>nul && "<userData>/picgo/win64/picgo.exe" u "<路径>"` |
| 自定义命令 | 模板里的 `${filepath}` / `${filename}` 占位符 |

**结果解析是整个功能里唯一能做成纯函数的部分，也是唯一容易写错的部分。**
从 `M(stdout, uploader)` 提取到的策略是"从最后一行往前扫，
收到 URL 就继续，遇到非 URL 行就立刻停止"：

> **停止条件是最关键的。** 不设它，日志里出现的任何网址都会被当成结果，
> 于是"上传 1 张图返回 3 个 URL"，回填时张冠李戴——而且看起来像是上传器的问题。
> 断言里专门有一条 `上传·日志头里的旧网址不被误收` 钉它。

数量校验同样不能省：`长度 !== 期望数量` 时直接报错，宁可失败也不让用户
拿着错位的地址去回填。

**回填走位置替换而不是字符串替换。** 从语法树里记下每个 Image 节点的精确区间，
按区间从后往前改。字符串替换会在"同一张图被引用两次""地址是另一张图地址的
子串"这些情况下出错。而且只替换 URL 那一段，保留 `![替代文字](` 与 `)`——
整段替换会丢掉用户写的替代文字。

全部改动汇入**一次** dispatch，Ctrl+Z 能一次性撤回整批替换；
逐张各撤一次的话，传了十张图就要按十次撤销。

> **自测抓到的一个真实缺陷。** 自定义命令的 `${filepath}` 最初是原样替换的，
> 含空格的路径（`C:/我的 图.png`）会被 shell 拆成两个参数，上传器只拿到前一半，
> 报"文件不存在"。现在按需加引号——但**不能无条件加**：模板里可能已经写了
> `"${filepath}"`，再加一层就变成 `""C:/a.png""`。

### 图片右键菜单在渲染出来的图片上右键，弹出 10 项操作：
上传图片、上传所有本地图片、转换图片语法、重命名 / 移动图片到、复制图片到、
打开图片位置、在浏览器中打开图片、复制图片地址、删除图片文件、重新加载所有图片。

**菜单用 DOM 自绘而不是 Electron 的原生 `Menu.popup()`**，理由是返回值：
原生菜单要通过 IPC 往返才能在渲染层拿到"用户点了哪一项"，而这些动作大多
只改文档（转换语法、改引用），本就在渲染层。自绘省掉一次往返，
也让菜单项能直接读当前编辑器状态来决定是否置灰。

**先反查文档位置，再决定哪些项可用。** 点击位置 → `posAtDOM` → 找到对应的
Image 节点 → 按它是不是本地图片决定置灰。查不到就整体置灰，
而不是让用户点了没反应：

```
图片右键菜单本地 10 项全可用 · 远程 5 项置灰 · 关闭无残留
```

远程图片置灰的 5 项（上传、重命名、复制、打开位置、删除）都需要本地文件，
点下去只会弹一句"没有本地文件可操作"，不如直接不让点。

**"转换图片语法"只改那一段。** Markdown ↔ HTML 互转，不动周围文字。

**"重命名 / 移动"的顺序是先改文件、成功了再改文档。** 反过来的话，
文件操作失败时文档里已经指向一个不存在的路径，用户看到的是图裂，
而且很难想到是"移动失败但引用已经改了"。

**删除走系统回收站，且不动文档里的引用**——用户可能正想把引用留着以后放新图。
删完引用会显示成"加载失败"占位，这本身就是一个明确的视觉提示。

> **菜单是"点了没反应也看不出来"的典型。** 回调没注册、位置反查失败、
> 菜单被立刻关掉——三种情况都只是"右键没反应"，没有任何报错。
> 所以断言落在一连串真实事件上：真的在渲染出来的图片上派发 `contextmenu`，
> 再数菜单项、数置灰项、确认关闭后 DOM 无残留。

## 数学公式与图表

### 解析器完全不认识数学公式用 **KaTeX** 渲染行内 `$…$` 与块级 `$$…$$`，按需加载。

打印解析树可以看到，`$E = mc^2$` 只是普通段落里的**文本**，`$$…$$` 也是普通段落。
`@lezer/markdown` 没有数学语法。所以公式的识别只能自己扫，
逻辑在 [`src/shared/数学.ts`](./src/shared/数学.ts)——是纯函数，可以逐条断言。

自己扫就要面对误判，最常见的是把货币金额当成公式。三条限制沿用
KaTeX auto-render 的通行约定：

1. 开头的 `$` **后面不能紧跟空白**
2. 结尾的 `$` **前面不能是空白**
3. 内容不能为空

```
数学·基本行内            =>  [E = mc^2]
数学·公式内允许空格       =>  [a + b]      ← 限制只作用在 $ 紧邻的位置
数学·单个美元符号不成公式  =>  （无）
数学·转义美元符号         =>  （无）       ← \$ 不是公式
数学·结尾前有空白不闭合    =>  （无）
```

### 块级装饰的硬约束——两条都踩过给块级公式加替换装饰时先报：

```
Decorations that replace line breaks may not be specified via plugins
```

加上 `block: true` 之后又报：

```
Block decorations may not be specified via plugins
```

**CodeMirror 完全禁止插件提供块级装饰**，加不加 `block` 都不行。原因是插件属于
视图层、随时可能销毁重建，而块级装饰会改变行的结构。只能来自 **StateField**。

所以块级公式与图表各开了一个 StateField，只负责自己那一件事；
其余装饰仍留在插件里——那里能拿到 `view.visibleRanges`，
长文档只处理视口内容，这个优势不该为了一处丢掉。

> **这个错误只有端到端测试能抓到。** 扫描器 14 条纯函数断言全绿，
> 装饰层的类名结构也都对——两处限制都是**运行时抛异常**，
> 而渲染层的异常被降级逻辑吞掉了，界面上只表现为"公式没渲染出来"。

### Mermaid 图表

` ```mermaid ` 围栏整块被替换成渲染出的 SVG。围栏在语法树里是标准的
`FencedCode` 节点，**不必像 `$$` 那样手工扫行**：找 `CodeInfo` 为 `mermaid`
的节点即可，缩进的围栏、波浪线 `~~~` 都能正确识别。

**失败时要把源码一并显示出来。** Mermaid 的报错信息往往很抽象
（`Parse error on line 3`），只给一句错误提示等于让人去猜哪一行写错了。

> **异步渲染的坑：不要靠文本内容判断状态。** 图表先出"正在渲染"占位，
> 异步换成 SVG。验证脚本一开始靠"文字里有没有『正在渲染』"判断是否渲染完，
> 结果**计数时对时错**，而且排查起来毫无头绪——因为判断依据本身就是渲染产物。
>
> 改成让 widget 自己标记：`<div class="cm-w-diagram" data-状态="渲染中|完成|失败">`。
> 等待逻辑、统计、调试工具都读这个属性。属性是明确的契约，文本只是给人看的。

```
图表渲染组件 3 个 · 出图 2 个 · 失败占位 1 个 · 未完成 0 个
```

断言分开数**出图 / 失败 / 未完成**——三者的修复方向完全不同。
"未完成"尤其重要：它意味着渲染流程卡住了，而不是渲染结果不对。

> **依赖代价。** Mermaid 12 让 `node_modules` 多了 116.7 MB，
> 构建时间从不到 1 秒变成约 23 秒。但它是**动态引入**的——
> 纯文字文档的用户不为它付启动成本，只是首次遇到图表时多等一瞬。

### 一个必然的连带变化块级替换把源码行从 DOM 里**移除**了，所以块级语法样本的「数学块行=3」
变成「数学公式=1」。这不是回归，是功能生效的结果。
光标移进公式或围栏时源码会重新露出来——按「光标是否落在区间内」判断而不是
按行：公式常常跨好几行，按行判断会让光标在其中任一行时整块都变回源码。

## 侧边栏与查找替换

### 侧边栏两个标签页：**大纲**与**文件树**。宽度可拖拽，显示状态与当前标签持久化在设置里。

**大纲**跟随光标高亮当前标题，点击跳转。几个边界值得记下来：

- `## 标题 ##` 的收尾井号必须剥掉，否则大纲里会出现「标题 ##」
- Setext 标题的下划线在语法节点**内部**，只取第一行才是正文
- 光标在**第一个标题之前**时返回 -1 并清空高亮，而不是错误地高亮第一个标题文档变了才重算标题，仅光标移动时复用缓存——重算要遍历整棵语法树，
而打字时每按一次键光标都会移动。

**文件树**以当前文档所在目录为根，目录在前、文件在后，各自按名称排序。
展开状态记在内存里，重新渲染不会丢失。

> **踩过的坑：并发刷新。** 打开文档、切换标签、显示侧边栏都会触发刷新，
> 而读目录是异步的。两次刷新交错时，后者先清空面板、前者再把内容写回去，
> 结果是**条目重复或内容对不上当前文档**。修法是序号守卫 + 把 DOM 写入
> 推迟到全部读完之后的**一次**提交（先建 DocumentFragment，再整体替换）。

### 类名沿用通用命名

`.selfmd-sidebar`、`.outline-item`、`.outline-expander`、`.outline-label`、
`.file-list-item`、`.file-node-content` —— 这些是主流编辑器主题里通用的类名，
因此针对它们写的主题规则有机会直接生效。

### 查找替换

`Ctrl+F` 查找、`Ctrl+H` 查找和替换、`F3` / `Shift+F3` 上下一个。

CodeMirror 的面板始终带替换行，没有「仅查找」模式。做法是「查找」打开时
给 `body` 加一个类把替换行藏起来，两个菜单项的行为差异对用户才可见。

**文案没有用 CSS 覆盖，而是走 CodeMirror 官方的本地化 Facet。**
面板里每个按钮、标签、输入框提示都是通过 `phrase(view, "next")` 取词的，
`EditorState.phrases` 就是用来注册译文的（见
[`src/renderer/src/editor/本地化.ts`](./src/renderer/src/editor/本地化.ts)）。

一开始我写的是 CSS `::after` 把原生英文盖掉，那是错的方向：

| | CSS 伪元素覆盖 | phrases Facet |
|---|---|---|
| 读屏软件读到的文字 | **仍是英文原文** | 中文 |
| CodeMirror 改版后 | DOM 一变就失效 | 不受影响 |
| 改动量 | 十几个选择器 | 一张键值表 |

键名大小写敏感，且**注册错了不报错、只是不生效**，所以宁可多列几个变体。

## 主题系统



### 三层级联

```
<userData>/themes/
├── github.css          ① 主题本体
├── base.user.css       ② 全局自定义 —— 对所有主题生效
└── github.user.css     ③ 该主题专属自定义 —— 换个主题就不生效
```

层叠顺序由 DOM 里 `<link>` 的先后决定，写在 `renderer/index.html`。
**顺序本身就是契约**，不能调换：用户永远压在主题之上，这样升级主题
不会冲掉用户的手改——内置 CSS
会在升级时被覆盖，所以用户改动必须放在别处。

②③ 不存在也没关系——浏览器对 404 的样式表静默忽略，不需要任何存在性检查。
这是通行做法。

### 主题可以是完整样式表，不只是变量

```css
/* 方式一：只覆盖变量 —— 最稳，跟着基础样式走 */
:root { --bg-color: #fbf8f1; --text-color: #2b2620; }

/* 方式二：直接写选择器 —— 表达力强，内容容器锚点是 #write */
#write .cm-lp-quote { border-left-width: 4px; }
```

两种可以混用。内置主题在 `src/main/services/builtin-themes.ts`，
其中「报刊」同时演示了两者。

### 主题资源目录主题旁边可以放**同名子目录**存字体、图片、光标，主题 CSS 用相对路径引用：

```
themes/
├── github.css
└── github/
    └── open-sans-….woff2      ← url('./github/….woff2') 能加载
```

`selfmd://theme/` 协议服务主题目录下的**任意文件**，不只是 `<主题名>.css`。
这是能用真实主题的前提：主题文件开头常常就是
三行 `@import "night/xxx.dark.css"`。

协议层有两道防护：显式拒绝含 `..` 的路径，解析后再确认结果仍落在主题目录内。

> **踩过的坑：CSP。** `selfmd:` 必须出现在**每一个**可能用到它的 CSP 指令里。
> 最初 `font-src` 漏了它——样式表照常生效，**只有字体悄悄回退成系统字体**，
> 肉眼极难发现是策略拦的。这个缺陷是主题协议自测（`子目录资源=200`）抓出来的。

### 变量契约：两层

| 层 | 例子 | 说明 |
|---|---|---|
| **通用变量层** | `--bg-color`、`--text-color`、`--side-bar-bg-color`、`--md-char-color`… | 命名与主流主题沿用同一套（共 37 个，用 `scripts/CSS变量契约.py` 扫出）。沿用它们的意义是**现成主题能直接迁移** |
| **本项目层** | `--bg-primary`、`--text-primary`、`--accent`… | 全部由上面派生（`--bg-primary: var(--bg-color)`）。表达本项目特有的语义 |

两层都定义在 `renderer/src/styles/base.css` 的 `:root` 里，而不是只在主题里——
主题缺失或写坏时应用仍要能用。

### 能做到与做不到的（重要）

另一种常见架构里，文档容器 `#write` 装的是**真实 HTML 元素**（`<h1>`、`<p>`、`<pre>`），
主题写的是 `#write h1 { … }`。selfMD 用 CodeMirror 6，内容是一堆 `div`。

| 主题写法 | 在 selfMD 里 |
|---|---|
| 覆盖变量（`:root { --bg-color: … }`） | ✅ 完整生效 |
| 基于通用类名的规则（`.md-fences`、`.md-task-list-item`、`.md-image`…） | ✅ 装饰层挂上了这些类名 |
| `#write .任意类 { … }` | ✅ 内容容器挂了 `id="write"` |
| 基于真实标签的规则（`#write h1 { … }`、`blockquote { … }`） | ❌ **不会命中**——CodeMirror 不产生这些标签 |

**因此不能宣称兼容第三方主题生态。** 能做到的是"变量与类名层面可迁移"，
标签层面的差异是架构性的，除非把编辑器换成渲染 DOM 的方案。

python scripts/CSS选择器.py <目录>           # 扫出所有 id/class，看主题挂钩了什么

## 资源与图标

```
resources/icon/
├── 源图.png          2048×1860 原始素材（不覆盖，重新生成时只读它）
├── logo-母版.png     1024×1024 从源图裁出的正方形母版
├── icon.png          256×256  应用窗口与"关于"对话框
├── icon-16/24/32/48/64/128/256/512.png
└── icon.ico          内嵌 7 种尺寸，供 Windows 任务栏与打包
```

重新生成：

```bash
pnpm icons              # 用默认阈值
pnpm icons -- 70        # 换一个阈值（数字越小，图案越小、留白越多）
```

脚本做三件事，都不靠肉眼估：

1. **找图案范围** —— 以边框像素的中位色为背景基准，逐像素算偏差，
   超过阈值的区域才算"图案"。阈值直接决定裁切紧致度。
2. **裁成正方形** —— 图标必须正方。取短边中心裁切，**不用补边**：
   源图背景本身有色差（左下 `#D6C5BB`、右中 `#B2A094`），补边容易补出接缝。
3. **生成 ICO** —— Windows 的任务栏与资源管理器需要多尺寸 ICO，
   单一尺寸会被系统拉伸。

### 阈值为什么可调源图的构图是**右下锚定**的：左侧与顶部有大片背景，右侧留白少，底部贴边。

```
阈值  40   左留白 14.5%  上留白 15.9%   图案偏小（初版用的值）
阈值 100   左留白 21.5%  上留白 26.3%   图案大 17.6%（现默认）
```

阈值调高**不是"切掉内容"，而是"不再把淡到看不见的背景渐变当成内容"**。
阈值 40 会把背景自身的渐变算进来，于是裁出来的方框里塞满近乎空白的区域，
图案在图标里就显得小。用 `python scripts/裁切阈值.py resources/icon/源图.png`
可以打印各阈值下的包围盒与四周留白，据此挑一个。

### 已知限制源图**没有透明通道**，且背景并非单一纯色（存在渐变），因此**没有做背景透明化**——
硬抠会留下脏边。图标表现为一块米色方块，这是可接受的。

若日后需要一个在 16×16 下依然清晰的任务栏图标，建议另做一版**简化标记**
（去掉文字与细节，只留主图形），而不是指望这张 2048×1860 的完整版缩到 16 像素。

## 中文化

**界面文案沿用通行的中文译法，不自己另译。**

理由不是省事，而是**切换成本**：用户已经对这套中文菜单形成了肌肉记忆。
把 `Source Code Mode` 译成"源码视图"、把 `Always on Top` 译成"窗口置顶"，
看着都对，但会在每次找菜单时多花半秒。照搬"源代码模式"、"保持窗口在最前端"、
"应用内窗口切换"，成本才是零。

译法来源与覆盖范围：

| 范围 | 条数 |
|---|---|
| 菜单（功能按键） | 147 条标签，全部含中文 |
| 界面通用（确定/取消/未命名…） | 按需取用 |
| 偏好设置项 | 37 项 / 5 个分区 |

少量专有名词**刻意保留英文**：`Markdown`、`YAML`、`GitHub`、`Electron`、
`CRLF`/`LF`，以及 `// eslint-disable-next-line` 这类翻译即失效的工具指令。
判断标准写进了 `scripts/check-i18n.mjs` 的「允许英文」列表。

### 为什么要有自动检查界面文案散落在三处（主进程菜单、IPC 对话框、渲染层提示），靠人工搜索一定会漏。
`scripts/check-i18n.mjs` 扫描所有 `.ts` 里承载文案的键（`label`/`title`/`message`/
`detail`/`buttons`/`toast`…），列出其中仍是英文的值。它已经抓出过两处真实遗漏：
状态栏的 `Ln 1, Col 1` 与文件外部变更的提示。

配套的 `scripts/check-encoding.mjs` 检查全部文本文件必须是合法 UTF-8、
不带 BOM、不含替换字符（乱码的确凿标志）、行尾符一致。中文一旦在某个环节走错
编码，结果不是报错而是**静默乱码**，所以这项检查不能靠肉眼。

两项检查都已接入 `pnpm verify`，菜单标签语言另有 82 项断言覆盖。

## 多文档标签

**一个视图，多份状态。** CodeMirror 6 的 `EditorState` **自带撤销历史**
（`history()` 把历史存在状态里，不是视图上），所以每个文档留一份状态，
切换时 `view.setState()`——**每个文档的撤销栈天然独立**，
不必自己拆栈，也不会"在甲文档里撤销把乙文档改回去"。

换成"每个文档一个 EditorView"也能做，但要处理多份 DOM、多份扩展、多份测量，
切换时还得销毁重建；收益只有"滚动位置各留一份"，不划算。

侧边栏加了「文档」标签列出已打开的文档：**有未保存改动的显示一个圆点**。
多文档下最容易忘记存盘，这个提示不能省。

### 唯一一处"顺序写错就静默丢数据"的地方

这是本轮最有价值的发现，而且**是回归测试抓出来的**：

```
多文档标签自测：起始2→新建后3→关闭后2
  甲标记在=true/切回后=false    ← 在甲里改、切到乙、再切回甲，改动没了
```

原因是 `file.new` 与 `openPath` 都写成：

```ts
doc.newDocument()
view.setState(新文档状态)      // ← 此刻视图里已经是新文档了
标签集.加入(doc.导出状态(), view.state)   // 读到的自然也是新文档
```

写回必须发生在**替换视图状态之前**：

```ts
标签集.存当前(view.state)      // 先存
view.setState(新文档状态)      // 再换
标签集.加入(doc.导出状态(), view.state)
```

顺序反了的后果是**"新建文件"会丢掉当前文档里未保存的改动**，
而且没有任何提示——用户只觉得"刚才写的东西不见了"。

> 这个约束没法在 `加入()` 内部自动满足：方法被调用时视图状态已经换掉了，
> 那一刻无论怎么读都拿不到旧文档的内容。所以只能靠契约与回归测试守住，
> `存当前()` 这个显眼的名字就是为此存在的。

修好之后的断言：

```
多文档标签   甲标记在=true/切回后=true 长度一致=true 乙内容未串=true
            撤销只影响乙=true 可重开=true 同文件去重=是
```

**同一个文件不开两份**也在测：两边内容会互相覆盖，而用户直到丢了一次改动才会发现。

### 导出设置

两个选项，放在偏好设置的「导出」分区里：

| 选项 | 默认 | 为什么 |
|---|---|---|
| 附带侧边目录 | **开** | 导出的 HTML 常常是给人看的，没有目录的长文很难导航 |
| 内嵌图片（单文件） | **关** | 内嵌会让文件大出好几倍；个人使用时图片通常就在同目录 |

菜单里的「导出设置」**直接打开偏好设置的导出分区**，而不是另做一个面板。
理由很实际：这两个键已经在偏好设置里了，再建一套界面就会出现
"两个地方改同一件事"，而它们迟早会不同步。

> `打开(定位分区)` 这个参数就是为此加的——用户点的是"导出设置"，
> 落在一个几十项的面板顶端还得自己往下找，等于没定位。

`exportIncludeOutline` / `exportEmbedImages` 必须在调用导出时**显式传给主进程**。
不传的话主进程会用自己的默认值，于是设置面板改了却没效果——
**那种"改了没反应"最难查**。

## 快速打开

Ctrl+P 唤起，输入即过滤，↑↓ 选择、Enter 打开、Esc 关闭。

**索引在面板打开时建一次，过滤全在本地做。** 每次敲键都查盘的话，
目录一大就会让每次按键卡一下——而"快速打开"的全部意义就在于快。

遍历目录有三个必须有的上限，否则不小心选到 `C:\` 就会把应用卡死：
跳过 `node_modules` / `.git` 一类的大目录、文件数上限 4000、深度上限 8。
深度限制还是符号链接成环时**唯一的护栏**。

### 打分的偏好不是凭感觉定的

只做"子序列能不能匹配上"的话，敲 `md` 会把几百个文件全列出来，
而想要的排在最后——那还不如直接翻文件树。所以匹配之外还要排序：

- **连续匹配**优于散落匹配（`abc` 命中 `abc.md` 好过 `a_b_c.md`）
- **词首**优于词中（`r` 命中 `README` 好过 `error`）
- **路径末段**优于目录名——用户记的是文件名，不是它所在的目录
- **越靠前**越好

```
匹配·空查询返回全部  =>  无关.md
匹配·命中文件名      =>  README.md
匹配·子序列命中      =>  note.md
匹配·前缀优于词中    =>  error.md
匹配·末段命中排前    =>  note.md
匹配·无命中返回空    =>  （空）
路径末段·反斜杠      =>  甲.md
```

断言大多是**相对顺序**而不是绝对匹配——排序质量才是这个功能的价值所在。

> **一个异步的坑。** 索引是异步建的，期间用户可能已经打了不少字。
> 所以索引回来之后必须按**当前**输入重算，而不是用建索引时捕获的旧值，
> 否则会出现"我明明打了字，列表却还是全量"。

## 命令实现率

`pnpm verify` 会从菜单摘要里把每个分类的 `(可用/总数)` 加起来，
报出一条**只该往上走的数字**：

```
菜单命令实现率                        98/98（灰着 0 项）
```

为什么值得单独断言：菜单项"能点但没反应"和"灰着不能点"是两回事，
而**注册表里的标记**与**实际有没有处理函数**是两处独立的信息。

本轮就抓到了**五处**不一致——`专注模式`、`打字机模式`、`上传图片`、
`上传所有本地图片` 四个命令的处理函数早就写好了，注册表里却还标着"未实现"，
于是菜单把它们灰掉了；`导出设置` 则是反过来，标记改对了却**根本没进菜单**。
两处的表现都是"这个功能好像没有"。

> 这类错标的隐蔽之处在于：**看起来一切正常**。菜单画得出来、代码也在，
> 只有真正去点的时候才会发现灰的。断言把"标记"和"能点"绑在一起检查，
> 才会在下一次忘记改标记时立刻报出来。
>
> 注册表的标记、菜单里的位置、实际的处理函数，是**三处独立的信息**。
> 任何一处漏了，用户看到的结果都一样：功能不存在。

现在 98 项菜单命令**全部可用**。这个数字的断言写法是下界（`可用 >= 92`）
而不是等值，所以新增命令时不必改断言，只有"灰着的项变多"才会失败。
