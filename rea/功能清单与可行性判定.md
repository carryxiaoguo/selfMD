## 1. 最重要的一条判定：Typora 的编辑器内核是什么

这决定了自研编辑器的可行性与技术选型，因此放在最前。

| 事实 | 证据 |
|---|---|
| 文本引擎是 **CodeMirror 5** | 🟢 `frame.js` 模块 `20`（偏移 1,010,557，161 KB）开头即 CodeMirror 的浏览器探测序言：`var e=navigator.userAgent,s=navigator.platform,p=/gecko\/\d/i.test(e),t=/MSIE \d/.test(e),l=/Trident\/...` |
| CodeMirror 相关标识出现 **178** 次 | 🟢 全文件正则计数 |
| 语法高亮模式**外置**为压缩包 | 🟢 `lib.asar` → `codemirror/mode.min.js`（566 KB） |
| 选区系统用 **rangy** | 🟢 `rangy` 出现 27 次；模块 `31` 导出 `rangy`（`e("31").rangy`） |
| 渲染层是 **contenteditable + 装饰 DOM** | 🟢 `contenteditable` 出现 141 次；`beforeinput` 2 次；`MutationObserver` 2 次 |
| 存在自研的 **brush / styler** 增量渲染层 | 🟢 `editor.brush.brushNode(cid)`、`editor.brush.clearAndPause()`、`editor.stylize.canContainInline()`、`editor.store(node)`、节点 `cid`（content id）体系 |
| **不是** ProseMirror / 富文本模型 | 🟢 `ProseMirror` 出现 **0** 次 |

### 🟡 结论：Typora 的"所见即所得"是这样实现的

```
纯 Markdown 文本（唯一真实数据源）
        ↓  CodeMirror 5 持有文档 + 光标/选区
        ↓  自研 markdown 解析器产出节点树（Node / NodeMap / TYPE）
        ↓  brush 层把节点"刷"成装饰 DOM（.md-image / .md-mathjax / .md-fences 等）
        ↓  行内元素用 contenteditable 的 inline 装饰模拟渲染外观
        ↓  用户编辑 → 反向映射回 Markdown 文本 → 写回 CodeMirror
```

**这是自研克隆唯一现实可行的技术路线**：Markdown 文本始终是唯一真实数据源（因此永远不会出现"富文本模型与 Markdown 互转丢信息"的问题），渲染只是叠加在文本之上的装饰层。

替代路线（ProseMirror/Tiptap 富文本模型）会导致 Markdown 往返转换必然有损，且要实现 Typora 的"源码模式与预览模式无损切换"极其困难。**不建议**。

## 3. 被加密层阻挡、无法"解析出来"的部分

必须明确：**"用 REA 解析出来"对主进程不成立**。

| 层 | 状态 | 影响 |
|---|---|---|
| `main.node`（1.10 MB 原生插件） | 🟢 全文件仅 1708 段可打印 ASCII，应用语义字符串命中数为 0 | 🔴 内部算法不可读 |
| `atom.js`（187 KB） | 🟢 base64 解码后 140,593 字节，entropy **7.999** | 🔴 密文，不可读 |

**但功能实现不受影响**，因为契约面完全可读：

- 🟢 **91 个 IPC 通道**已全量枚举（`JSBridge.invoke("...")` 正则扫描）→ 主进程提供的能力清单
- 🟢 **300+ 菜单项**、**Panel.json 全部设置项**、**Front.json 全部 UI 字符串** → 行为规格
- 🟢 **87 个渲染层模块**（除模块 `20` 为 CodeMirror 第三方）→ 业务逻辑全可读

即：**我们知道它有哪些能力、参数形状、调用时机、用户可见行为；不知道的是主进程内部如何实现**（例如 `app.download` 是否处理重定向/超时/代理）。自研时这些按需求重新实现即可，不存在"解析不出来就做不了"的问题。

## 4. 工作量现实评估

| 口径 | 估算 |
|---|---|
| Typora 渲染层原始 TS 规模 | 🟡 约 30–50 万行（1.64 MB 压缩后 ≈ 10:1 展开比） |
| 加上第三方资产（MathJax 2.3 MB、Mermaid 3.3 MB、CodeMirror modes 566 KB、pdf 工具链） | 可直接复用开源版本，无需自研 |
| **单人全职达到 Typora 1.9.5 全功能等价** | 🟡 **12–24 个月** |
| 达到"日常写作可用、覆盖 90% 使用频率" | 🟡 **4–8 周** |
| 在本次协作中（多轮迭代）可交付 | 见 §5 分期 |

**直白结论**：「功能要求和 Typora 一模一样」作为**终局目标**可以设定，但它不是一个会话、甚至不是几十个会话能完成的事。**唯一可行的推进方式是按使用频率排序、逐域交付可运行版本**，而不是先铺开所有功能的骨架。

## 6. 与商业授权有关的边界（仅一次提醒）

Typora 是商业闭源软件。基于 REA 结果**自行重写实现供个人使用**，与**复制其代码/资产再分发**是两件事：

- ✅ 可做：按观察到的行为规格自行实现；引入 MathJax/Mermaid/CodeMirror 等**各自开源许可**的第三方库
- ❌ 不要做：直接搬运 `frame.js`/`atom.js` 的代码或其反混淆产物；打包分发 `lib.asar`/`node_modules.asar` 中的资产；把自研版本对外分发
- 📌 自用、不分发，风险面最小。若日后要分发，需重新评估并替换所有非自研资产。

### P2 期间被验证机制抓出的三个真实缺陷

这三个都不是理论担忧，而是"逐项对账"这一验证方式直接暴露出来的实现错误：

1. **语法高亮与装饰层共用 class 名**，导致同一段文字被标记两层——
   解析树 `StrongEmphasis=1`，DOM 里 `.cm-md-strong` 却有 4 个。
   修法：语法高亮改用 `cm-tok-*` 前缀，与装饰层彻底分离。
2. **用 `RangeSetBuilder` 构建装饰**，它只接受互不重叠的区间，遇到嵌套直接抛异常；
   为规避异常而加的"重叠即跳过"过滤，又把嵌套强调的内层整条丢掉——
   解析树 `Emphasis=2`，屏幕上只有 1 个斜体。修法：改用 `RangeSet.of(区间, true)`。
3. **紧凑测试样本违反 Markdown 块级分隔要求**：去掉空行后，表格末行与紧随的
   `---` 被解析成 Setext 标题，整个表格从语法树里消失。修法：样本保留空行，
   改由冒烟测试把窗口调高来保证全文档落在一屏内。

### 一个值得记录的方法论结论

**验证方式本身要有能力发现"静默失效"。** 装饰层的失败模式几乎都是沉默的：
节点名写错、区间顺序不对、class 名冲突——都不会报错，只会少画一点东西。
因此 P2 的验证没有停留在"能跑起来"，而是建立了**双计数对账**机制：

- **解析树计数**（语法树里各类节点有多少个）覆盖整篇文档；
- **渲染 DOM 计数**（装饰元素实际有多少个）只覆盖视口。

两者放在一起，才能区分"装饰没生效"和"内容在屏幕外被虚拟化"。
上述三个缺陷全部是靠这组数字对不上而暴露的。
